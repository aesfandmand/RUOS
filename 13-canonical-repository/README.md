# Canonical Repository Specification v0.1

وضعیت: `implemented-draft`

این بخش ساختار مرجع مخزن RUOS را برای نگهداری دانش، موجودیت‌ها، قابلیت‌ها، صفحات، سفرها، الگوها، طرح‌ها، قوانین و خروجی‌های اجرایی تعریف می‌کند.

## هدف

- یک منبع حقیقت نسخه‌بندی‌شده برای همه پروژه‌ها
- جداسازی دانش عمومی، دانشیِ دامنه و دانش اختصاصی پروژه
- جلوگیری از تولید داده و محتوای تکراری
- امکان استفاده مشترک وب‌سایت، اینستاگرام، CMS، API و موتورهای هوش مصنوعی
- حفظ منشأ، مالک، وضعیت تأیید، نسخه و تاریخچه هر شیء
- آماده‌سازی ورودی استاندارد برای Enterprise Assembly Engine

## اصل مرجع

> One canonical object → many governed views

صفحه، مقاله، ویدئو، مسیر خرید، مسیر سرمایه‌گذاری و خروجی شبکه اجتماعی، نسخه مستقل حقیقت نیستند؛ هرکدام نمایی از اشیای مرجع مخزن هستند.

## فضای نام

هر شیء باید در یکی از فضای نام‌های زیر قرار گیرد:

- `global`: قابل استفاده در همه پروژه‌ها
- `industry`: مشترک در یک صنعت یا حوزه
- `project`: اختصاصی یک پروژه
- `brand`: اختصاصی یک برند
- `implementation`: وابسته به فناوری یا کانال
- `archive`: منسوخ یا تاریخی و غیرقابل استفاده در تولید جدید

نمونه UID:

```text
ruos:project:red-umbrella:page:structures-hub
ruos:project:red-umbrella:entity:structure:unipole
ruos:global:capability:knowledge-graph-architecture
```

## قرارداد فایل شیء

هر فایل مرجع باید حداقل این داده‌ها را داشته باشد:

- `uid`
- `kind`
- `namespace`
- `version`
- `status`
- `title`
- `summary`
- `source`
- `governance`
- `relationships`

داده‌های تأییدنشده باید با وضعیت `pending` یا `candidate` ثبت شوند و نباید به‌صورت فکت قطعی در صفحه منتشر شوند.

## پوشه‌های مرجع

### `00-governance`
قانون اساسی، سیاست‌ها، قواعد ارث‌بری، اولویت منابع، تأیید و آرشیو.

### `01-enterprise`
تعریف سازمان، برندها، مأموریت‌ها، اهداف و مدل عملیاتی RUOS.

### `02-domains`
دانش مشترک حوزه‌ها؛ مانند طراحی وب، تبلیغات محیطی، سئو و معماری محتوا.

### `03-projects`
فضای مستقل هر پروژه و نگاشت آن به هسته مشترک.

### `04-entities`
رکورد مرجع موجودیت‌ها مانند سازه، خدمت، مکان، کمپین، پروژه و پرسونا.

### `05-capabilities`
توانمندی‌های قابل استفاده مجدد، شواهد، ورودی‌ها، خروجی‌ها و روابط آن‌ها.

### `06-knowledge`
قواعد، تصمیم‌ها، الگوها، واژه‌نامه، FAQ، مقالات، ویدئوها و بلوک‌های دانشی.

### `07-journeys`
پرسونا، نیت، مرحله سفر، نقاط ورود، تبدیل‌های خرد و تبدیل‌های اصلی.

### `08-pages`
تعریف صفحه به‌عنوان نمای مونتاژی از دانش، قابلیت، سفر و اجزای طراحی.

### `09-templates`
قالب‌های هاب، پیلار، کلاستر، موجودیت، خدمت، پروژه، مقاله و ویدئو.

### `10-design-system`
توکن‌ها، اجزا، الگوهای تعاملی، موشن و دسترس‌پذیری.

### `11-writing-system`
استاندارد فارسی، لحن برند، واژگان ترجیحی، نگارش سئو و AI.

### `12-gcera-dsl`
زبان توصیفی رسمی و Schemaهای آن.

### `14-assembly`
قواعد بازیابی، انتخاب بلوک، مونتاژ صفحه، SEO، Schema و خروجی کانال‌ها.

### `15-runtime`
قراردادهای اجرای درخواست، وضعیت، کش، اعتبارسنجی و پاسخ.

## چرخه عمر

```text
draft → candidate → review → approved → canonical → published
                                      ↘ deprecated → archived
```

فقط اشیای `approved` یا `canonical` مجازند وارد خروجی رسمی شوند. استثناها باید صریح، ثبت‌شده و قابل ردگیری باشند.

## قواعد الزام‌آور

1. هر UID فقط یک رکورد مرجع فعال دارد.
2. Viewها اجازه کپی‌کردن حقیقت مرجع را ندارند.
3. فایل پروژه می‌تواند هسته عمومی را توسعه دهد، اما بدون تصمیم صریح آن را بازنویسی نمی‌کند.
4. تصمیم متأخر تأییدشده، نسخه قبلی را `superseded` می‌کند؛ حذف نمی‌کند.
5. اسناد LOCKED و تصمیم‌های نهایی کارفرما باید در provenance ثبت شوند.
6. هر صفحه باید روابط Knowledge Graph و Capability Layer متناسب با نیت خود را اعلام کند.
7. زبان فارسی مبنای اولیه پروژه‌های فعلی است؛ محلی‌سازی پس از تأیید نسخه فارسی انجام می‌شود.
8. طراحی تأییدشده Structure v16 تا زمان ثبت نسخه جایگزین تأییدشده، baseline است.
