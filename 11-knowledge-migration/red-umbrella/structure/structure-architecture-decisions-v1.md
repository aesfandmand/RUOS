## 2. Canonical mission of `/structures`

`/structures` نه صفحه فروش، نه صفحه سرمایه‌گذاری و نه صفحه اجاره است.

ماموریت آن:
- دانشنامه و کاتالوگ مادر تمام سازه‌ها
- منبع داده مرکزی برای تمام صفحات وابسته
- نمای قابل جست‌وجو، فیلتر و طبقه‌بندی پایگاه داده سازه‌ها
- ارائه شناخت کامل بدون فشار تبدیل مستقیم
- نمایش مسیرهای مرتبط برای کاربرانی که قصد خرید، سرمایه‌گذاری، اجاره یا فروش سازمانی دارند

اصل حاکم:

> Structure Page = Master Knowledge & Data Source

## 4. Taxonomies and filters

تاکسونومی صفحه نباید فقط «نوع سازه» باشد.

فیلترهای اصلی تاییدشده یا صریحاً درخواست‌شده:
- نوع سازه
- ایندور / اوتدور
- ابعاد
- تعداد وجه
- افقی / عمودی
- نوع نوردهی
- نور از جلو / پشت / داخل / دوطرفه
- ثابت / دیجیتال
- محل مناسب نصب
- هدف تبلیغاتی
- کارکرد
- مسیر تجاری مرتبط
- نوع مخاطب
- امکان خرید / سرمایه‌گذاری / اجاره / فروش سازمانی

فیلدهایی که تاکسونومی عمومی نیستند و باید به‌صورت داده ساختاری رکورد ذخیره شوند:
- جزئیات نقشه
- مشخصات فونداسیون
- وزن دقیق
- دیتیل اتصال
- محدودیت اجرایی خاص
- شرایط نگهداری ویژه

- صفحه خرید ایندور
- صفحه خرید اوتدور
- هاب سرمایه‌گذاری
- صفحه اجاره تابلو
- صفحه فروش سازمانی
- صفحات کمپین
- صفحات محصول
- بلاگ
- ویدئو
- نمونه‌کار
- صفحات شهر و موقعیت

اصل:

> هیچ صفحه‌ای نباید نسخه جداگانه و متناقضی از اطلاعات سازه تولید کند.

## 6. Knowledge Graph layer

لایه نالج‌گراف باید در تمام صفحات، متناسب با پیلار، کلاستر و خوشه همان صفحه حضور داشته باشد.

### Required relationships

Structure:
- IS_A → Structure Type
- HAS_FEATURE → Technical Feature
- HAS_LIGHTING → Lighting Type
- HAS_ORIENTATION → Horizontal / Vertical
- HAS_FACE_COUNT → Face Count
- SUITABLE_FOR → Location
- SERVES → Business Goal
- SERVES → Persona
- SUPPORTS → Campaign Type
- AVAILABLE_FOR → Purchase / Investment / Rent / Organizational Sale
- RELATED_TO → Service
- RELATED_TO → Project
- RELATED_TO → Article
- RELATED_TO → Video
- RELATED_TO → City
- REQUIRES → Foundation
- REQUIRES → Installation Method
- PRODUCED_BY / BUILT_BY → Capability or business unit

### Page-level rule

هر صفحه باید:
- موجودیت اصلی خود را مشخص کند
- روابط اصلی را نمایش یا در داده ساختاری پیاده کند
- از روابط برای لینک‌سازی داخلی استفاده کند
- فقط نالج‌گراف مرتبط با نیت همان صفحه را فعال کند

## 7. Capability Layer

Capability Layer باید از ابتدای معماری تعریف شود و نقش تزئینی یا مستندسازی صرف نداشته باشد.

برای هر Capability باید روشن باشد:
- چه کاری انجام می‌دهد
- چه مسئله‌ای را حل می‌کند
- برای کدام پرسوناست
- چه ورودی‌هایی نیاز دارد
- چه خروجی‌ای تولید می‌کند
- در کدام مرحله سفر کاربر ظاهر می‌شود
- با کدام سازه، خدمت، پروژه و CTA مرتبط است
- چه شواهد یا نمونه‌کاری آن را اثبات می‌کند

### Capability roles in Structure ecosystem
- تحقیق و نیازسنجی
- انتخاب سازه
- مهندسی و طراحی
- ساخت
- نصب
- جانمایی
- برنامه‌ریزی شبکه سازه‌ها
- امکان‌سنجی سرمایه‌گذاری
- بهره‌برداری
- نگهداری
- فروش رسانه
- اجرای کمپین
- تولید محتوا و طراحی تبلیغ

## 9. Architectural governance

قانون اجرایی تاییدشده:

> پیش از طراحی یا تولید هر صفحه، معماری کل سایت باید لایه‌به‌لایه مرور شود؛ هر بخش فقط پس از اصلاح و تایید کارفرما مبنای ادامه است.

ترتیب حاکم:
1. مرور معماری
2. تعیین نیت و پرسونا
3. تعیین پیلار، کلاستر و خوشه
4. تعیین موجودیت‌ها و روابط Knowledge Graph
5. تعیین Capability Layer
6. تعیین مسیر تبدیل
7. طراحی محتوا
8. طراحی UX/UI
9. اجرا
10. QC

## 10. Superseded architecture

موارد زیر منسوخ محسوب می‌شوند:
- تعریف `/structures` به‌عنوان دروازه اصلی خرید
- نمایش سازه‌ها فقط براساس یک تاکسونومی «نوع سازه»
- استفاده از صفحه Structure به‌عنوان صفحه فروش مستقیم
- تولید اطلاعات مستقل و تکراری برای هر مسیر
- افزودن Knowledge Graph یا Capability Layer در انتهای اجرا

## 11. Open decisions

هنوز از منبع ارائه‌شده پاسخ قطعی برای این موارد استخراج نشده است:
- URL نهایی و نام دقیق صفحات خرید ایندور و اوتدور
- سطح دسترسی داده‌های بسیار فنی و نقشه‌ها برای عموم
- مالک اصلی داده سازه‌ها میان چتر قرمز و ایران تابلو
- مدل دقیق همگام‌سازی موجودی قابل اجاره با رکورد مادر سازه
- مرز نهایی میان رکورد «نوع سازه» و رکورد «محصول قابل فروش»

این موارد باید در مرور جزءبه‌جزء معماری تعیین تکلیف شوند.
